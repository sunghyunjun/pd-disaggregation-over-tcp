## 초록

프리필과 디코드를 서로 다른 GPU에 나누는 분리 서빙(PD disaggregation) 연구는 대부분 GPU 사이를 RDMA나 NVLink 같은 고속 연결로 잇는 환경을 전제한다. 그러나 임대 클라우드처럼 GPU 사이의 데이터가 일반 이더넷(TCP)을 거쳐야 하는 환경도 흔하다. 이 연구는 AWS의 GPU 인스턴스 세 종류에서 vLLM과 NIXL/UCX를 TCP 위에 올리고 Gemma 4 26B(MoE)와 31B(dense)를 1~3노드로 구성해 389회 측정했다. 결함 점검을 거친 256회를 분석에 썼다.

분리로 늘어나는 첫 토큰 추가 지연(TTFT overhead)은 거의 전부 KV 캐시 전송 시간이었고 측정 전에 계산으로 예측할 수 있었다. 실효 전송 대역폭은 클라우드가 연결 하나에 허용하는 상한의 1.3~1.7배에 머물렀다. 시스템 전체의 백분위 지표로는 문제없어 보여도 요청 하나하나를 보면 상당수가 응답 도중에 멈췄고 이 멈춤이 분리의 손익을 가른다. 응답 도중의 끊김을 50~75 ms 이내로 막아야 하는 서비스에서는 분리가 유리하다. 입력이 4K 토큰인 26B 모델에서는 GPU당 처리 가능 부하가 1.5~4배 높았고 SLO를 지킨 토큰당 원가는 약 3배 낮았다. 31B dense 모델의 대화형 서비스에서는 분리 구성만 SLO를 지켰다. 반면 대화처럼 입력이 짧을 때는 이득이 없었고 끊김을 100 ms 이상 허용하면 차이가 대부분 사라졌다. 가중치가 무거울수록(NVFP4보다 FP8·BF16) 분리의 이득이 커졌다. 이 결과를 바탕으로 분리 도입 여부를 미리 판단하는 점검표를 제시하고 측정 도구와 요청별 원자료를 공개한다.

## 1. 서론

대규모 언어 모델 서빙에서 한 요청은 두 단계를 거친다. 입력 전체를 한 번에 처리하는 프리필(prefill)과 출력 토큰을 하나씩 만드는 디코드(decode)다. 두 단계를 같은 GPU에서 섞어 돌리면 긴 프리필이 디코드를 가로막아 이미 응답 중인 요청의 토큰 흐름이 끊긴다. 분리 서빙은 두 단계를 서로 다른 GPU에 맡겨 이 간섭을 없애고 프리필이 만든 KV 캐시(어텐션의 키·값을 저장한 캐시)를 디코드 GPU로 보낸다[DistServe, Splitwise, Mooncake].

분리의 대가는 KV 캐시 전송이다. 기존 연구는 이 전송이 충분히 빠르다고 전제한다. DistServe와 Splitwise는 노드 안의 NVLink나 노드 사이의 InfiniBand를, Mooncake는 RDMA(원격 직접 메모리 접근) 네트워크를 쓴다. 그러나 현실의 추론 인프라는 더 다양하다. 추론용 GPU의 종류가 늘었고 노드 하나에 GPU가 한 장뿐인 인스턴스도 많다. 임대 클라우드에서는 네트워크를 고를 수 없어 GPU 사이의 데이터가 일반 이더넷을 타야 하는 경우가 흔하다. 이런 환경에서 분리가 성립하는지를 두고는 "TCP는 매우 느리다"는 경고가 있을 뿐 측정 수치는 드물다[vLLM 문서, NVIDIA Dynamo 문서].

최근에는 느린 연결에서 분리를 다룬 연구도 나오기 시작했다. Prefill-as-a-Service는 상용 이더넷으로 데이터센터 사이에 KV 캐시를 보내고[PrfaaS], PDD는 TCP 광역망으로 데이터센터 사이의 분리를 구성한다[PDD]. llm-d 프로젝트는 TCP 위에서 KV 전송 라이브러리의 성능 차이를 측정했다[llm-d]. 앞의 연구들은 대규모 클러스터 사이에서 동작하는 자체 시스템이다. 이 연구는 방향이 다르다. 공개된 설계를 공개 도구(vLLM, NIXL)로 그대로 쓰고 임대 클라우드의 GPU 노드 사이 TCP 연결에서 분리가 언제 이득인지를 측정한다.

이 연구는 GPU 사이에 빠른 연결이 없어 KV 캐시가 일반 네트워크를 타야 하는 환경을 대상으로 하고 그중 노드 사이의 TCP 연결을 측정했다. 연구 질문(research question, RQ)은 네 가지다.

- RQ1. 느린 TCP 연결에서도 분리가 서비스 수준 목표(SLO)를 지키는 처리량(SLO 굿풋)을 높일 수 있는가.
- RQ2. 첫 토큰 추가 지연은 무엇이 정하는가.
- RQ3. 분리는 어떤 조건에서 이기는가.
- RQ4. 노드를 늘릴 때 프리필과 디코드의 비율을 어떻게 정해야 하는가.

이 연구의 기여는 다음과 같다.

- 요청 단위로 SLO를 판정하는 방법과, SLO 기준을 바꿔 가며 결론의 민감도를 확인하는 분석을 제시한다.
- 첫 토큰 추가 지연이 KV 전송 시간과 같음을 보이고 이를 계산하는 모델로 측정 전에 예측해 검증했다.
- 입력 길이, 가중치 정밀도, 모델 크기, 끊김 허용치에 따라 분리의 손익 경계가 어떻게 움직이는지 보인다.
- 3노드로 늘릴 때 병목이 있는 쪽을 늘려야 한다는 비율 규칙을 제시한다.
- 측정 도구와 요청별 원자료를 공개하고, 효과가 없었던 설정과 기법도 결과와 함께 보고한다.

## 2. 배경과 관련 연구

**분리 서빙.** DistServe는 프리필과 디코드를 나눠 각각의 지연 목표에 맞게 자원을 배치하고 목표 달성률 90%일 때의 GPU당 굿풋을 지표로 삼았다[DistServe]. 이 연구도 같은 지표 체계를 따른다. Splitwise는 두 단계의 하드웨어 요구가 다르다는 점에 착안해 서로 다른 기종에 나눠 배치했고 InfiniBand로 KV를 층별로 전송했다[Splitwise]. Mooncake는 KV 캐시를 중심으로 분리 구조를 설계해 대규모 서비스에 적용했다[Mooncake]. TetriInfer, DéjàVu, P/D-Serve도 같은 계열이다. 이들은 모두 고속 연결을 전제한다.

**함께 두기의 개선.** Sarathi-Serve는 프리필을 작은 조각으로 나눠 디코드와 섞는 청크 프리필(chunked prefill)로 간섭을 줄였다[Sarathi-Serve]. 이 연구의 복제본 구성도 청크 프리필을 쓴다. Sarathi-Serve는 토큰 간격 SLO를 간섭 없는 디코드 스텝 시간의 5배(엄격)와 25배(느슨)로 정의했다. semi-PD는 한 GPU 안에서 연산 자원을 나누는 절충안을 제시했다[semi-PD].

**KV 전송 계층.** vLLM은 NIXL 라이브러리로 KV를 전송하고 NIXL은 UCX 등 여러 전송 백엔드를 감싼다. UCX는 RDMA가 없으면 TCP를 쓴다. CacheGen은 KV 캐시를 압축해 네트워크 전송량을 줄였다[CacheGen].

**느린 연결에서의 분리.** Prefill-as-a-Service는 혼합 어텐션 모델의 KV가 작다는 점을 이용해, 상용 이더넷으로 데이터센터 사이에 KV를 보내는 구조를 제안했다[PrfaaS]. PDD는 TCP 광역망으로 연결된 두 클러스터 사이에서 분리를 구성하고 전송을 계산과 겹치기 위한 중계 디코드를 도입했다[PDD]. llm-d 프로젝트는 100 Gbps TCP에서 GPU 간 전송이 UCX로는 0.55 GB/s, UCCL로는 약 4.7~4.9 GB/s라고 보고했다[llm-d]. NVIDIA는 분리가 프리필 비중이 크고 모델이 클 때 가장 효과적이라고 정리했다[Beyond the Buzz]. <span class="todo">※ 원문 대조 필요: Dynamo 문서의 TCP 저하 배수, Beyond the Buzz의 해당 문장</span>

**이 연구의 위치.** 위 연구들이 대규모 클러스터에서 새 시스템을 설계했다면, 이 연구는 기본 vLLM을 임대 GPU 노드에 그대로 올려 측정한다. 전송 시간을 미리 계산하는 모델과 도입 판단 기준을 함께 제시한다. 같은 조건을 측정한 연구는 찾지 못했지만 조사가 완전하지 않으므로 이 연구가 최초라고 주장하지는 않는다.

## 3. 측정 방법

### 3.1 환경

AWS us-east-1의 한 가용 영역에서 GPU 인스턴스 세 종류를 썼다. 모두 노드당 GPU가 한 장이다(표 1). 같은 가용 영역 안에서 TCP 연결 하나의 대역폭 상한은 약 4.97 Gbps였다. 클러스터 배치 그룹(cluster placement group, 인스턴스를 네트워크상 가까운 곳에 모아 두는 AWS 기능)에 넣으면 이 상한이 9.54 Gbps로 올라갔다. g7e의 명목 대역폭 50 Gbps는 연결 여덟 개를 합쳐야 도달했다(49.72 Gbps). 부하 생성과 요청 중계는 별도의 CPU 인스턴스에서 했다.

| 인스턴스 | GPU | GPU 메모리 | 주로 쓴 실험 |
|---|---|---|---|
| g7.2xlarge | RTX PRO 4500 | 32 GB | 두 노드의 입력 길이 비교, 전송 경로 조정 |
| g6e.2xlarge | L40S | 48 GB | GPU 간 비교, L40S 두 노드 |
| g7e.2xlarge | RTX PRO 6000 | 96 GB | GPU 간 비교, 클러스터 배치 그룹, 2~3노드 스케일링, 반복 측정 |

<p class="cap">표 1. 측정에 쓴 GPU 인스턴스. g7e는 시간당 3.363달러(온디맨드)로 원가 계산에 썼다.</p>

소프트웨어는 vLLM v0.30.0을, 전송에는 NIXL의 풀(pull) 방식 커넥터를 썼다. UCX의 TCP 세그먼트 크기는 기본값 8 KB에서 256 KB로 올렸다(4.2절). 청크 프리필 크기는 2,560 토큰, GPU 메모리 사용률은 0.90이다.

### 3.2 모델과 KV 크기

Gemma 4의 26B-A4B와 31B 두 모델을 썼다. 26B-A4B는 토큰마다 일부 전문가 층만 쓰는 혼합 전문가(MoE) 구조로 활성 파라미터가 약 4B이고 31B는 모든 파라미터를 쓰는 dense 구조다. 둘 다 전역 어텐션과 슬라이딩 윈도 어텐션을 섞은 혼합 어텐션 구조다. 정밀도로는 NVIDIA의 4비트 부동소수점 형식인 NVFP4 체크포인트를 주로 썼고 비교를 위해 FP8(가중치만 양자화)과 BF16도 썼다. NVFP4 체크포인트는 KV 캐시를 FP8로 저장하고 FP8·BF16 체크포인트는 BF16으로 저장한다. 그래서 같은 26B 모델이라도 4K 토큰 입력 한 건의 전송량이 NVFP4는 140 MB(입력 토큰당 약 34 KB), FP8은 280 MB로 두 배 차이가 난다. 31B NVFP4는 560 MB(입력 토큰당 약 137 KB)다.

### 3.3 구성

같은 GPU 수에서 두 방식을 비교했다. 복제본(replica) 구성에서는 각 노드가 프리필과 디코드를 모두 하는 서버를 띄우고 요청을 번갈아 나눈다. 분리 구성에서는 프리필 전용 노드(P)와 디코드 전용 노드(D)를 둔다. 프리필 노드 x대와 디코드 노드 y대로 이루어진 분리 구성은 xPyD로 적는다. 두 노드에서는 복제본 둘과 1P1D를, 세 노드에서는 복제본 셋과 1P2D, 2P1D를 비교했다. 단일 노드는 GPU 간 비교에만 썼다.

### 3.4 워크로드

세 종류를 썼다. 대화형은 ShareGPT 대화(입력 중앙값 약 80~100 토큰, 출력 약 100~150 토큰)다. 긴 입력은 입력 길이를 4,096, 16,384, 32,000 토큰으로 고정하고 출력을 512 토큰으로 고정한 합성 요청이다. 실제 트레이스는 Azure의 공개 대화 트레이스 600건(입력 중앙값 996, 출력 217 토큰)이다. 요청은 정해진 평균 요청률을 따르는 포아송 과정으로 보냈고 한 측정은 180초다.

### 3.5 지표와 SLO

요청 하나가 SLO를 지켰는지를 요청 단위로 판정한다. 대화형 SLO는 첫 토큰 시간(TTFT, 요청을 보낸 뒤 첫 출력 토큰이 오기까지의 시간) 1초 이하, 요청 안의 최대 토큰 간격(ITL, 연속한 두 출력 토큰 사이의 시간) 50 ms 이하다. 문서형 SLO는 각각 3초와 250 ms다. 요청 안의 최대 간격을 쓰는 이유는 500토큰 답변 중 한 번의 긴 멈춤이 토큰 비율로는 0.2%에 불과해 백분위 통계에 잡히지 않지만, 사용자는 바로 그 끊김을 느끼기 때문이다.

달성률은 SLO를 지킨 요청의 비율이다. 지원 부하는 달성률 0.9 이상인 가장 높은 요청률이고 반복 측정한 지점은 모든 반복이 0.9 이상이어야 인정한다. SLO 굿풋은 SLO를 지킨 요청의 출력 토큰 처리량이고 원가는 GPU 시간당 요금을 SLO 굿풋으로 나눈 토큰 100만 개당 달러다.

첫 토큰 1초는 설계상의 선택이다. 선행 연구의 첫 토큰 목표는 응용과 모델에 따라 0.125초에서 30초까지 넓게 퍼져 있다(DistServe의 코드 완성 0.125초와 챗봇 0.25~4.0초, Mooncake의 실제 트레이스 실험 30초). 1초는 사용자가 흐름이 끊겼다고 느끼기 시작하는 응답 시간으로 알려진 값이다[Nielsen]<span class="todo">※ 원문 대조 필요</span>. 결과가 이 기준에 얼마나 의존하는지는 4.6절에서 따로 확인한다.

### 3.6 절차와 데이터 선별

모든 측정은 접두어 캐시(prefix cache)를 끄고 했다. 초기 측정 일부에서는 캐시를 켠 채 같은 시드의 요청을 반복해서 앞 측정의 요청이 뒤 측정에서 캐시에 적중하는 오염이 생겼다. 모든 측정을 점검해 이런 측정 122회를 제외했고 폐기 기준에 걸린 측정과 서버 기동 실패를 더해 389회 중 128회를 뺐다. 클라이언트 중계 서버가 CPU 한계에 닿은 5회는 주의 데이터로 따로 표시했다. 결과는 나머지 256회로 계산했다.

신뢰도를 확인하는 마지막 측정에서는 서버마다 워밍업 요청 30건을 보낸 뒤, 주요 지점을 시드를 바꿔 세 번씩 쟀다. 첫 토큰 중앙값은 반복 사이에서 5% 안으로 움직였고 하루 전 측정과도 거의 같았다(부록 그림 A5). 달성률이 0.85~0.95인 지점만 반복 사이에서 최대 ±0.09 흔들려 판정이 갈릴 수 있었다. 그래서 이런 지점은 본문에서 "경계"로 표시한다. 측정 회차와 공개 데이터 폴더의 대응은 부록 C에 정리했다.

## 4. 결과

4.1절은 판정 방법을 정한다. 4.2절과 4.3절은 RQ2, 4.4절과 4.6절은 RQ3, 4.5절과 4.7절은 RQ1과 RQ4에 답한다. 4.8절은 실제 트레이스와 정확성으로 결과를 보완한다.

### 4.1 시스템 백분위는 요청별 멈춤을 가린다

<!-- FIG fig01_request_vs_system | 그림 1. 시스템 전체의 토큰 간격 p99(가로, 로그)와 요청 단위 대화형 달성률(세로). 첫 토큰 p99가 1초 미만인 안전 측정 166회. 점선 왼쪽 아래는 시스템 p99가 예산 안인데도 달성률이 0.9에 못 미친 측정이다. -->

시스템 전체의 토큰 간격 p99는 모든 요청의 모든 간격을 한데 모아 계산한다. 이 지표로는 문제가 없어 보여도 요청 단위로 보면 상당수 요청이 응답 도중에 멈춘다(그림 1). 첫 토큰 p99가 1초 미만인 측정 166회 가운데, 시스템 p99가 50 ms 이하인데 달성률이 0.9에 못 미친 복제본 측정이 18회였다. 예를 들어 g7e 두 대의 복제본에서 26B FP8 모델에 4K 입력을 초당 0.5건 보냈을 때 시스템 p99는 8.6 ms였지만, 요청의 48%가 한 번 이상 예산을 넘는 멈춤을 겪어 달성률은 0.52였다. 이 멈춤은 다른 요청의 프리필이 끼어들 때 생긴다. 이후의 모든 판정은 요청 단위로 한다.

### 4.2 전송 경로: 처음엔 소프트웨어, 다음엔 연결당 상한

<!-- FIG fig03_network | 그림 2. (a) 클러스터 배치 그룹 안 g7e 두 대 사이의 병렬 TCP 연결 수별 대역폭. (b) 파란 막대는 iperf로 잰 TCP 연결 하나의 대역폭 상한, 주황 막대는 vLLM이 KV 캐시를 실제로 보낸 속도(전송량 ÷ 전송 시간)다. 회색 점은 UCX 세그먼트 크기, NIXL 스레드 수, 조각 크기 등 설정 네 가지를 바꿔 잰 KV 전송 속도로, 모두 주황 막대와 거의 같다. -->

기본 설정에서 전송을 막은 것은 네트워크가 아니라 소프트웨어였다. UCX의 TCP 세그먼트 기본값 8 KB가 병목이었다. 256 KB로 올리자 KV 전송이 3.0~4.05 Gbps에서 7.07~8.49 Gbps로 두 배가 되었다. g7 두 대에서 4K 입력을 초당 0.25건 보낼 때 첫 토큰 중앙값은 626 ms에서 466 ms로 줄었고, 초당 1건에서 대화형 달성률은 0.82에서 0.99로 올랐다.

그다음에는 클라우드가 연결 하나에 허용하는 대역폭이 전송을 막았다. 클러스터 배치 그룹을 쓰자 이 상한이 4.97 Gbps에서 9.54 Gbps로 두 배 올랐다(그림 2b의 파란 막대). KV 캐시의 실제 전송 속도는 클러스터 배치 그룹 밖에서 6.55 Gbps(상한의 1.32배), 안에서 13.96 Gbps(1.46배)로 상한을 따라 올라갔다(그림 2b의 주황 막대). 상한보다 조금 높은 것은 NIXL이 한 요청의 KV를 여러 조각으로 나눠 여러 연결에 싣기 때문이다. 조각이 많은 31B 모델은 1.68배까지 올라갔다. 반면 세그먼트를 1 MB로, NIXL 스레드를 16개로 늘리거나 조각 크기를 키우는 설정은 모두 13.58~14.43 Gbps 안에 머물러 효과가 없었다(그림 2b의 회색 점). 인스턴스 전체의 대역폭은 남아 있었다. 연결 수를 늘리면 대역폭이 거의 비례해 늘어, 연결 여덟 개에서 명목 대역폭 50 Gbps에 닿았다(그림 2a). 남은 여유는 설정이 아니라 연결 수에 있다.

대역폭을 인위적으로 제한해 보면 이 상한이 곧 첫 토큰을 정한다(부록 그림 A1). g7 두 대에서 4K 입력을 초당 0.5건 보낼 때 첫 토큰 중앙값은 제한이 없을 때 471 ms, 3 Gbps에서 744 ms, 2 Gbps에서 954 ms, 1 Gbps에서 2,185 ms였고, 대화형 달성률은 각각 1.00, 0.92, 0.55, 0이었다.

두 가지는 효과가 없거나 해로웠다. KV를 GPU가 아닌 호스트 메모리를 거쳐 보내는 모드는 첫 토큰을 초당 0.25건에서 4.7배, 1건에서 75배 늦췄다. 클라우드 네트워크의 크레딧(순간 대역폭 허용량)은 제약이 되지 않았다. L40S 두 대에 4K 입력을 15분 연속으로 보냈을 때 평균 전송은 0.91 Gbps로 상한의 18%였고, 부하 전후의 단일 연결 대역폭은 4.967과 4.966 Gbps로 같았다.

### 4.3 첫 토큰 추가 지연은 KV 전송 시간이다

<!-- FIG fig04_ttft_decomposition | 그림 3. 분리 구성의 첫 토큰 중앙값을 단일 노드의 첫 토큰, KV 전송 시간, 잔차로 나눈 것. 검은 세로선은 측정 전에 식 1로 적어 둔 예측값이다. -->

분리로 늘어난 첫 토큰 지연, 곧 첫 토큰 추가 지연은 거의 전부 KV 전송을 기다리는 시간이다. g7e 두 대에서 26B FP8에 4K 입력을 초당 0.5건 보낼 때, 클러스터 배치 그룹으로 연결당 상한을 두 배 올리자 평균 전송 시간이 324 ms에서 165 ms로 줄었고 첫 토큰 중앙값은 482 ms에서 351 ms로 줄었다(그림 3). 줄어든 양이 거의 같다. 전송이 없다고 가정한 첫 토큰(351 − 165 = 186 ms)은 같은 지점의 단일 노드 첫 토큰 158 ms에 가깝다.

이 관계를 식으로 쓰면 다음과 같다.

<div class="eq">TTFT<sub>분리</sub> ≈ TTFT<sub>단일</sub> + (입력 토큰 수 × 입력 토큰당 전송 바이트) ÷ (연결당 상한 × <i>m</i>) + 잔차 <span class="eqno">(1)</span></div>

여기서 <i>m</i>은 여러 연결에 나눠 싣는 효과로 1.3~1.7이고 잔차는 첫 디코드 스텝과 스케줄링 시간이다. 이 식을 3노드 측정 전에 적어 두고 측정과 비교했다. 전송량은 26B NVFP4 140 MB, 31B NVFP4 560 MB로 예측과 정확히 같았다. 첫 토큰은 26B 4K 초당 1건에서 예측 235 ms, 실측 267 ms(단일 130 + 전송 84 + 잔차 53)였고, 31B 4K 초당 0.25건에서 예측 810~830 ms, 실측 853 ms(단일 483 + 전송 283 + 잔차 87)였다. 31B의 잔차가 큰 것은 첫 디코드 스텝이 25 ms로 26B(6.5 ms)보다 길기 때문으로 보인다.

이 식이 있으면 분리를 도입하기 전에 첫 토큰 예산 안에 전송이 들어가는지 계산할 수 있다. 예를 들어 연결당 상한이 약 5 Gbps인 환경에서 26B FP8의 16K 입력은 전송만 1초가 넘어, 대화형 첫 토큰 예산 1초를 지킬 수 없다.

### 4.4 두 노드에서 분리는 언제 이기는가

<!-- FIG fig05_input_length | 그림 4. g7 두 대, 26B NVFP4, 초당 0.5건에서 입력 길이에 따른 달성률. (a) 대화형 SLO, (b) 문서형 SLO. -->

**입력 길이가 가른다.** g7 두 대에서 26B NVFP4에 초당 0.5건을 보냈을 때, 4K 입력의 대화형 달성률은 분리 0.96, 복제본 0.23이었다(그림 4a). 복제본은 첫 토큰이 아니라 토큰 간격에서 실패했다. 16K부터는 분리의 전송 시간이 1초를 넘어 두 구성 모두 대화형 SLO를 지키지 못했다. 문서형 SLO에서는 16K에서도 분리가 0.47로 복제본 0.17보다 나았다(그림 4b). 32K에서는 모든 구성이 실패했다. 대화 길이의 짧은 입력에서는 두 구성의 차이가 없었다.

**GPU가 빨라지면 격차가 좁아진다.** 4K 입력 초당 1건에서 PRO 4500, L40S, PRO 6000(FP8)의 복제본은 달성률 0.02~0.14로 무너졌고 분리는 0.83~0.98이었다(부록 그림 A2). 빠른 GPU일수록 디코드 스텝이 짧아 프리필 간섭을 견딜 여유가 생긴다. PRO 6000에서 NVFP4로 가중치를 가볍게 하고 클러스터 배치 그룹을 쓰자 복제본도 0.97을 지켰다.

<!-- FIG fig10_quantization | 그림 5. 같은 두 노드(g7e)에서 26B 모델의 가중치 정밀도만 바꾼 비교. 같은 날 한 번에 측정했다. -->

**가중치 정밀도가 이득의 폭을 바꾼다.** 같은 두 노드에서 26B의 정밀도만 바꿔 보면(그림 5), 4K 입력 초당 1건에서 복제본의 달성률은 NVFP4 0.97, FP8 0.13, BF16 0.03이었다. 분리는 세 정밀도 모두 1.00이었다. 복제본의 실패는 모두 토큰 간격 때문이었고 첫 토큰 p99는 1초 안이었다. 가중치가 무거울수록 4K 프리필 한 번이 디코드를 오래 멈춰 세운다. FP8과 BF16에서는 분리가 사실상 유일한 선택이고 NVFP4에서는 복제본도 어느 정도 버텨 격차가 줄어든다. 대화형 ShareGPT 초당 16건에서는 정밀도와 관계없이 분리의 이득이 없었다. BF16에서는 두 구성 모두 실패했다.

분리의 첫 토큰은 KV 크기를 따라 늘었다. 4K 초당 1건에서 NVFP4 269 ms, FP8 362 ms, BF16 448 ms였다. FP8과 BF16 체크포인트는 KV를 BF16으로 저장해 전송량이 두 배이기 때문이다. 다만 프리필 속도 차이도 섞여 있어 전송의 몫만 따로 떼어 내지는 않았다.

### 4.5 세 노드로 늘릴 때와 비율 규칙

<!-- FIG fig08_scaling_26b | 그림 6. 26B NVFP4, g7e 클러스터 배치 그룹. 가로축은 GPU당 요청률이다. (a) 4K 입력, (b) ShareGPT 대화형. 세로 막대는 반복 측정의 범위, 속 빈 점은 클라이언트 한계 구간이다. -->

**26B, 4K 입력: 분리가 GPU당 용량을 늘린다.** 복제본은 GPU당 초당 2건에서 세 번 모두 실패했다(0.48~0.64). 1P1D는 GPU당 3건(초당 6건)에서 1.00, 4건에서 0.84였다(그림 6a). 통과한 부하끼리 비교하면 3배, 가장 보수적으로 잡아도 1.5배 이상이다. 세 노드로 늘려도 GPU당 효율은 1P1D를 넘지 못했다. 1P2D는 GPU당 3건(초당 9건)에서 0.906으로 경계였고 초당 12건에서 프리필 대기열이 쌓여 첫 토큰 중앙값이 14.3초가 되었다. 2P1D는 초당 9건에서 디코드 한 대가 간격을 지키지 못해 0.77이었다. 26B의 4K 입력에서는 프리필 한 대와 디코드 한 대가 감당하는 양이 비슷해 1:1이 균형이다.

**26B, 대화형: 이득이 없다.** GPU당 초당 8건에서는 모든 구성이 통과했다(그림 6b). 그 위의 부하는 클라이언트 중계 서버가 한계에 닿아 판정에서 뺐다. 이 구간에서 2P1D가 무너진 원인은 서버 지표로 확인했다. 디코드 한 대가 동시 시퀀스 상한 256에 걸려 대기열이 868건까지 쌓였고 KV 사용률은 43%에 불과했다. 대화형은 디코드 쪽을 늘려야 한다.

<!-- FIG fig09_scaling_31b | 그림 7. 31B NVFP4, g7e 클러스터 배치 그룹. (a) ShareGPT 대화형, (b) 4K 입력. 세로 막대는 반복 측정의 범위다. -->

**31B, 대화형: 분리만 SLO를 지킨다.** 복제본 둘은 초당 2건에서도 세 번 모두 0.43~0.49였다(그림 7a). dense 모델의 디코드 스텝이 길어 짧은 프리필의 간섭만으로도 간격이 50 ms를 넘는다. 1P1D는 초당 4건에서 0.98로 안정적으로 통과했고 초당 8건은 0.863~0.944로 경계였다.

**31B, 4K 입력: 어느 구성도 안정적으로 지키지 못한다.** 복제본은 간격으로, 분리는 첫 토큰으로 실패했다(그림 7b). 31B의 4K 프리필 한 번이 약 480 ms이고 전송이 약 280 ms 더해져 첫 토큰 예산 1초에 여유가 거의 없다. 1P1D 초당 0.25건과 2P1D 초당 0.75건이 세 번 중 한 번씩만 0.9를 넘었다. 같은 초당 0.75건의 대화형 굿풋은 2P1D 290, 1P2D 177, 복제본 셋 8 tok/s였다. 긴 입력을 받는 31B는 프리필 쪽을 늘려야 한다.

이를 정리하면 병목이 있는 쪽을 늘리도록 비율을 정한다. 26B의 4K 입력은 1:1, 31B의 4K 입력은 프리필, 26B의 대화형은 디코드다.

### 4.6 결론은 SLO 기준에 얼마나 의존하는가

<!-- FIG fig15_slo_sensitivity | 그림 8. 첫 토큰 기준(세로)과 요청 안 최대 토큰 간격 기준(가로)을 바꿔 가며 계산한, GPU당 SLO 굿풋의 분리 ÷ 복제본 비율. D와 R은 한쪽만 달성률 0.9에 닿은 칸, ≤·≥는 한쪽이 측정 범위 끝까지 통과해 실제 비율이 더 작거나 클 수 있는 칸, ?는 양쪽 다 끝까지 통과해 가를 수 없는 칸이다. 굵은 테두리는 1초·50 ms다. -->

요청별 원자료가 모두 남아 있어, SLO 기준을 바꿔 가며 같은 측정을 다시 판정할 수 있다. 첫 토큰 기준 0.25~5초와 최대 간격 기준 30~300 ms의 조합마다, 모든 반복이 달성률 0.9를 넘는 가장 높은 요청률에서 잰 GPU당 SLO 굿풋을 두 방식끼리 비교했다(그림 8).

분리가 이기는 영역은 분명하다. 응답 도중의 끊김을 엄격하게 막을 때, 대체로 최대 간격 기준이 50~75 ms 이하일 때다. 26B의 4K 입력(g7e 클러스터 배치 그룹)은 40 ms 이하에서 분리만 통과했고 비율은 50 ms에서 3.0배, 75 ms 이상에서는 2배 이하로 줄었다. 31B 대화형은 40~75 ms에서만 분리가 단독으로 통과했고 100 ms 이상에서는 두 구성 모두 측정 범위 끝까지 통과했다. 31B의 4K 입력은 첫 토큰 기준 1초에서는 둘 다 실패했지만 1.5초로 늘리면 분리만 통과했다. 반대로 g7e FP8의 대화형은 어떤 기준에서도 복제본이 나았다(0.3~0.7배).

<!-- FIG fig16_frontier | 그림 9. SLO 없이 본 지연과 처리량. 가로는 GPU당 출력 토큰 처리량, 위 줄은 요청별 첫 토큰의 p90, 아래 줄은 요청별 최대 토큰 간격의 p90이다. -->

SLO를 정하지 않고 지연과 처리량의 관계를 그대로 보면 이유가 드러난다(그림 9). 모든 조합에서 복제본은 첫 토큰이 빠르고 분리는 요청별 최대 간격이 짧다. 26B 4K 복제본의 최대 간격 p90은 50~65 ms로 50 ms 선에 붙어 있어, 이 지점의 판정은 50 ms라는 선택에 민감하다. 31B 대화형의 복제본은 70~90 ms, 분리는 35~48 ms로 차이가 뚜렷하다. 분리는 첫 토큰을 내주고 매끄러운 토큰 흐름을 얻는 거래다. 그 거래의 가치는 서비스가 끊김을 얼마나 싫어하느냐에 달려 있다.

GPU 사이의 차이도 SLO를 넣으면 제원표보다 커진다(부록 그림 A3). 같은 26B FP8 모델에 KV 용량을 똑같이 맞춰도 단일 노드의 대화형 지원 부하는 L40S가 초당 1건, PRO 6000이 초당 16건이었다. SLO 원가는 3.15달러 대 0.34달러로 9.2배 차이였다. 다만 두 값은 서로 다른 날 쟀다.

### 4.8 실제 트레이스, 정확성, 푸시 전송

Azure 대화 트레이스를 두 노드(초당 약 3.9건)와 세 노드(초당 약 5.9건)에서 재생했다(부록 그림 A4). 26B는 모든 구성이 통과했고 원가도 같았다. 차이는 첫 토큰뿐이어서 분리가 전송 시간만큼 약 120 ms 늦었다. 이 부하는 26B 각 구성의 상한보다 낮아 어느 구성이 나은지 가르지 못한다. 31B는 두 구성 모두 실패했다. 복제본은 간격(달성률 0.05)이, 분리는 첫 토큰 꼬리(0.28)가 원인이다.

분리 구성이 문맥을 제대로 옮기는지도 확인했다. 채팅 양식의 짧은 질문 여섯 개와 약 4K 토큰의 긴 질문 두 개를 온도 0으로 보내, 짧은 질문은 단일 노드와 출력이 같은지, 긴 질문은 핵심 단어가 충분히 겹치는지 비교했다.

KV를 디코드 쪽이 가져가는 대신 프리필 쪽이 밀어 넣는 푸시 방식은 31B 4K에서 전송 시간을 27~36%, 첫 토큰 중앙값을 53~62 ms 줄였지만 달성률 차이는 ±0.04에 그쳤다(부록 그림 A6). KV 전송을 층별로 프리필 계산과 겹치는 vLLM의 제안 패치(PR #56874)는 KV 캐시 그룹이 하나인 모델만 지원해, 혼합 어텐션인 Gemma 4에서는 첫 요청부터 멈췄다.

## 5. 논의

### 5.1 연구 질문에 대한 답

**RQ1. 느린 TCP 연결에서도 분리가 SLO 굿풋을 높일 수 있는가.** 조건부로 그렇다. 4K 토큰 입력의 26B 모델에서 분리는 GPU당 지원 부하를 1.5~4배 높였고 SLO를 지킨 토큰당 원가를 약 3배 낮췄다. 31B dense 모델의 대화형 서비스에서는 분리 구성만 SLO를 지켰다. 반면 26B의 대화형 서비스에서는 이득이 없었다(4.5절, 4.7절).

**RQ2. 첫 토큰 추가 지연은 무엇이 정하는가.** KV 전송 시간이다. 전송 시간은 입력 토큰 수와 입력 토큰당 전송 바이트에 비례하고 실효 대역폭에 반비례한다(식 1). 실효 대역폭은 처음에는 전송 소프트웨어의 설정이, 설정을 고친 뒤에는 클라우드의 연결당 상한이 정한다(4.2절, 4.3절).

**RQ3. 분리는 어떤 조건에서 이기는가.** 두 조건이 함께 맞아야 한다. 복제본에서 프리필 간섭으로 생기는 요청 안의 최대 토큰 간격이 서비스의 끊김 허용치를 넘어야 하고, 분리로 생기는 전송 시간이 첫 토큰 예산 안에 들어가야 한다. 입력이 길수록, 가중치가 무거울수록, dense 모델일수록 첫째 조건을 만족하기 쉽다. 끊김 허용치가 100 ms 이상이면 차이가 대부분 사라진다(4.4절, 4.6절).

**RQ4. 노드를 늘릴 때 비율을 어떻게 정해야 하는가.** 병목이 있는 쪽을 늘린다. 26B의 4K 입력은 1:1이 가장 효율적이었고, 31B의 4K 입력은 프리필을, 26B의 대화형은 디코드를 늘려야 했다(4.5절).

### 5.2 분리를 도입하기 전에 확인할 것

측정 결과를 도입 판단 기준으로 옮기면 네 가지다.

1. **끊김 허용치와 프리필 간섭.** 복제본에서 요청 안 최대 토큰 간격이 서비스의 끊김 허용치를 넘는가. 넘지 않으면 분리는 첫 토큰만 늦춘다. 가중치가 무겁고 dense일수록, 입력이 길수록 넘기 쉽다.
2. **전송 여유.** 입력 토큰 수 × 입력 토큰당 전송 바이트 ÷ 실효 대역폭이 첫 토큰 예산 안에 드는가(식 1). 클라우드의 연결당 상한과 클러스터 배치 그룹 여부가 실효 대역폭을 정한다.
3. **전송 소프트웨어 설정.** UCX의 TCP 세그먼트 크기처럼 기본값이 병목인 설정을 먼저 고친다. 그 뒤에 남은 여유는 설정보다 연결 수에 있다.
4. **비율.** 병목 쪽을 늘린다. 긴 입력의 큰 모델은 프리필, 짧은 입력의 대화형은 디코드다.

RDMA나 AWS EFA가 있는 환경에서는 식 1의 연결당 상한과 <i>m</i>이 크게 달라져 전송 항이 작아진다. 그러면 첫 토큰의 대가가 줄어 분리가 이기는 영역이 넓어질 것이다. 이 연구는 RDMA 기준점을 직접 재지 않았다. 연결당 상한을 넘으려면 전송을 더 많은 연결에 나눠 싣는 방법이 필요하다. llm-d가 보고한 UCCL이 한 예다.

## 6. 한계

- 모델 계열이 Gemma 4 하나이고 둘 다 혼합 어텐션이다. 전역 어텐션만 쓰는 모델은 토큰당 KV가 더 커서 전송 항이 커진다.
- vLLM 한 버전(v0.30.0), AWS 한 리전의 한 가용 영역, 최대 세 노드에서 쟀다.
- RDMA 기준점이 없다. 노드 안의 느린 연결(NVLink나 P2P 없이 PCIe로 잇는 경우)도 재지 않았다.
- 요청률 간격이 거칠고 느슨한 SLO에서 복제본의 상한은 측정 범위 밖에 있다.
- 접두어 캐시 재사용이 없는 조건이다. 멀티턴이나 공통 시스템 프롬프트처럼 캐시 적중이 많은 워크로드는 프리필과 전송이 줄어 결론이 달라질 수 있다.
- 시간은 클라이언트에서 쟀으므로 중계 서버에서 걸린 시간이 포함된다. 대화형 고부하 일부는 클라이언트 한계 구간이라 판정에서 뺐다.
- 일부 비교(GPU 간 KV 맞춤 비교)는 서로 다른 날의 측정을 잇는다.

## 7. 결론

느린 TCP 연결에서도 분리 서빙은 조건부로 SLO 굿풋을 높인다. 첫 토큰 추가 지연은 KV 전송 시간이며 미리 계산할 수 있다. 분리가 이득인 것은 서비스가 응답 도중의 끊김을 엄격하게 막아야 하고, 입력이 길거나 모델이 무거워 프리필 간섭이 크며, 그 입력의 전송 시간이 첫 토큰 예산 안에 들어갈 때다. 이 조건은 입력 길이, 토큰당 KV 바이트, 연결당 대역폭, 끊김 허용치라는 네 숫자로 측정 전에 판단할 수 있다.

### B. 실무에서 겪은 함정

- UCX의 TCP 수신 세그먼트가 송신 세그먼트보다 작으면 엔진이 아예 뜨지 않는다. 두 값을 함께 올려야 한다.
- 높은 요청률에서 요청 중계 서버가 운영체제의 파일 핸들 한도(기본 1,024)에 걸려 요청이 실패했다. 분리 구성의 중계 서버는 요청마다 연결을 두 개 열어 더 빨리 한도에 걸린다.
- vLLM v0.30.0의 트레이스 재생은 요청 수를 지정하지 않으면 빈 목록을 만들어 실패한다.
- 같은 시드의 요청을 접두어 캐시를 켠 서버에 반복해서 보내면 뒤 측정이 앞 측정이 남긴 캐시에 적중해 결과가 부풀려진다.

### D. AI 도구 사용

측정·분석 스크립트 작성, 클라우드 인프라 운영, 그림 초안 작성에 AI 코딩 도구(Claude)를 썼다. 모든 실험은 실제 하드웨어에서 수행했고 모든 수치는 저자가 원자료와 대조했다.
